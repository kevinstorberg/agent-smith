## Describe What, Not How

The ticket describes desired capabilities and outcomes, not implementation details.

1. Tasks describe what the system should do, not how to code it — no specific endpoint routes, class names, or function signatures
2. Technical context is provided for understanding the problem, not as implementation instructions
3. The ticket does not dictate specific framework methods, internal architecture, or code patterns unless they are genuine constraints
4. The engineer reading the ticket has freedom to choose the implementation approach
