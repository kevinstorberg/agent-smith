# Deployment Guide

This guide keeps deployment docs stateless. Infrastructure details change by app,
so Cairn documents the boundaries and commands the template owns. Your deployment
platform should own provider-specific manifests, image registries, secrets stores,
and scaling policy.

## Configuration Boundaries

Runtime configuration:

- `.env.default` is committed and documents supported runtime variables.
- `.env.{APP_ENV}` is local or deployment-specific.
- Real environment variables override `.env` files.
- `src/settings.py` is the code source of truth for runtime settings.

Structural configuration:

- `config/default.yaml` owns default backend and LLM settings.
- `config/graphs/*.yaml` owns graph-specific overrides.
- `config/models.py` owns the YAML schema.

Database URLs:

- Prefer `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`,
  `POSTGRES_PASSWORD`, and `POSTGRES_DB_<ENV>`.
- Use `DATABASE_URL_<ENV>` only for explicit full-URL overrides.
- Use `Settings.database_url_for(env)` instead of rebuilding URLs in app code.

## Local Runtime

```bash
cp .env.default .env.development
docker compose up -d db redis
poetry run alembic upgrade head
poetry run uvicorn src.app:app --reload
```

If local ports are taken:

```bash
POSTGRES_PORT=55432 REDIS_PORT=56379 docker compose up -d db redis
APP_PORT=18011 docker compose up app
```

The checked-in [docker-compose.yml](../docker-compose.yml) is the local Compose
source of truth. Do not maintain a second copied Compose file in docs.

## Production Container

The checked-in [Dockerfile](../Dockerfile) is the production image source of
truth. It builds a non-root runtime image, installs only main dependencies, and
defines the container healthcheck against `/health`.

Generic Docker shape:

```bash
docker build -t cairn-app .
docker run --rm -p 8000:8000 --env-file <runtime-env-file> cairn-app
```

Keep [docker-compose.yml](../docker-compose.yml) for local development. Your
deployment platform should own image tags, registries, secrets, probes, scaling,
TLS, and rollout policy.

## Production Checklist

1. Set `APP_ENV=production`.
2. Provide production database settings or `DATABASE_URL_PRODUCTION`.
3. Replace `SECRET_KEY` with a long random secret.
4. Set explicit hosts and origins; do not deploy with wildcard production
   `TRUSTED_HOSTS` or CORS origins.
5. Provide model/provider keys required by your graph builders.
6. Select persistent backends in YAML when the app needs persistence or multiple
   processes.
7. Install optional dependency groups required by selected backends.
8. Run Alembic migrations before serving traffic.
9. Expose `/health` through the platform health check.
10. Keep secrets in the platform secret manager or environment, not committed
   files.

Backend switching details live in [BACKENDS.md](BACKENDS.md).

## Production Security

Cairn wires production security at the app boundary: trusted host checks,
security headers, rate limiting, and request body size limits are middleware,
not router or service code. Local defaults stay permissive for fast development,
but `APP_ENV=production` fails startup and doctor checks unless production
security values are explicit.

Runtime variable names live in `.env.default` and `src/settings.py`. Structural
security options live in `config/default.yaml` and `config/models.py`.

For production, set a non-template `SECRET_KEY`, explicit trusted hosts, and
explicit CORS origins. Enable HSTS only when TLS termination and proxy behavior
are correct for the deployment.

The built-in rate limiter is an in-process guard for template defaults and
single-process deployments. Use edge or WAF rate limiting as the outer control
for internet-facing production systems, especially when running multiple app
processes.

## Migrations

Development flow:

```bash
poetry run alembic revision --autogenerate -m "describe change"
poetry run alembic upgrade head
poetry run alembic downgrade -1
```

Before production migrations:

- Review autogenerated migrations.
- Verify backward compatibility with the version serving traffic.
- Back up data or confirm the platform backup policy.
- Avoid long blocking operations on large tables.
- Test downgrade or roll-forward recovery.

## Health Checks

The template ships a basic health endpoint at `/health`. Keep it cheap and
dependency-light. Add deeper dependency checks only if your platform can tolerate
temporary provider degradation without causing unnecessary restarts.

## Secrets

Never commit `.env.production`, private keys, provider credentials, or generated
secret files. The root `.gitignore` should own those patterns.

If your platform provides secret files instead of environment variables, adapt
`src/settings.py` or load those files at process startup. Keep that adapter small
and deployment-specific.

## Troubleshooting

- Database connection failure: inspect selected `APP_ENV`, `POSTGRES_*` values,
  and any `DATABASE_URL_<ENV>` override.
- Settings changed but tests still read old values: call `reset_settings()`.
- Redis or S3 failures: verify the selected YAML backend, optional dependency
  group, and provider credentials.
- Migration mismatch: inspect Alembic history and `alembic_version` before
  stamping or dropping anything.
